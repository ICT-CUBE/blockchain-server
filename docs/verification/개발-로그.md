## 3. 아키텍처 핵심 결정사항

### 3.1 컨트랙트 (TASK-01~03)
- **UUPS 업그레이더블 프록시** + **AccessControl 역할 분리** (`DEFAULT_ADMIN_ROLE`, `MINTER_ROLE`, `AUTHORIZED_TRANSFER_ROLE`, `PAUSER_ROLE`, `UPGRADER_ROLE`).
- **표준 ERC-721 `transferFrom`/`safeTransferFrom`을 의도적으로 비활성화**하고, 소유자의 EIP-712 서명 동의(`OwnerConsent`)를 relayer가 제출하는 `authorizedTransfer`만 허용 — 임의 P2P 이전을 막고 모든 소유권 이전이 ARZONE 승인 흐름을 거치도록 강제.
- **Burn 함수 없음** — ABI에 노출되지 않음을 테스트로 고정.
- **Mainnet 트랙에서만** admin이 컨트랙트(Timelock)여야 하고 delay가 정확히 48h여야 하는 `assertValidGovernanceConfig` 규칙으로 로컬/Amoy와 Mainnet의 거버넌스 엄격도를 분리.

### 3.2 서버 아키텍처 (TASK-04~14)
- **fake/real 어댑터 포트 패턴**을 전 영역에 일관 적용: `CustodialWalletPort`(Web3Auth), `PinningPort`/`PreservationPort`(Pinata/NFT.Storage) 모두 `provider=fake|real` 환경변수로 전환. 외부 credential 없이도 전체 파이프라인을 실제로 실행/테스트 가능.
- **HMAC 인증 + 승인 JWT 이중 게이트** (TASK-06): 모든 내부 API는 HMAC 필수, NFT 소유권을 바꾸는 라우트만 추가로 승인 JWT(`jti` 원자적 바인딩으로 재사용 방지) 요구.
- **멱등성**: idempotencyKey 기반 Operation 생성 원자화, `(tokenId, cid)` unique constraint로 metadata 재요청 멱등 처리, HMAC nonce 1회성 강제.
- **트랜잭션 제출 (TASK-10)**: nonce는 DB(`SignerNonceReservation`)로 조정, 서명 직후 broadcast 전 raw transaction은 AES-256-GCM으로 암호화해 저장 후 broadcast 성공 시 폐기, 5분 이상 미확정 시 RBF(수수료 인상 재제출), RBF 최대 시도 초과 시 REVIEW_REQUIRED.
- **Confirmation (TASK-11)**: 5 confirmations 기준, 재시작 시 DB 상태만으로 in-flight Operation을 전부 재개(in-memory 상태 없음).
- **Webhook 알림 (TASK-12)**: outbox 패턴, exponential backoff+jitter 재시도, 수동 `redeliver` CLI (HTTP Admin API는 의도적으로 만들지 않음).
- **Metadata (TASK-13)**: 이미지→canonical JSON 순서로 pin, hot-pin 성공 여부만 Mint 게이트(READY) 조건으로 삼고 장기보존(NFT.Storage) 실패는 격리(비차단).
- **감사/실패 기록 (TASK-14)**: `AuditWriter` 단일 창구로 allowlist projection + 금지 key 자동 검사(redaction). 운영자 조회 API(`/internal/v1/audit/*`)는 Backend 연동용 HMAC 키와 **별도의 `HMAC_OPERATOR_*` 키 scope**로 분리 — 조회 권한과 쓰기 권한이 서로 다른 credential.

### 3.3 테스트 전략
- 태스크마다: 순수 unit → 실제 로컬 MySQL + 실제 로컬 Hardhat 노드 기반 integration → 전체 HTTP 스택 기반 e2e 순으로 검증.
- Fresh Hardhat 노드 재기동 + 컨트랙트 재배포 + 테스트 DB 전체 TRUNCATE를 매 회귀 실행 전에 수행하는 것을 표준 절차로 확립 (아래 5절 참조).

## 4. 개발 중 발견한 주요 이슈와 해결

| 이슈 | 원인 | 해결 |
|---|---|---|
| MySQL InnoDB 데드락 | 같은 트랜잭션 안에서 `INSERT` 직후 `SELECT...FOR UPDATE`를 거는 패턴이 동시 요청 시 데드락 | 행 부트스트랩을 `INSERT...ON DUPLICATE KEY IGNORE`로 트랜잭션 밖에서 먼저 수행 |
| ethers `AbstractProvider` 250ms 캐시 | `getBlockNumber()`가 `evm_mine` 직후에도 캐시된 값을 반환해 confirmation 카운트가 멈춤 | `JsonRpcProvider` 생성 시 `cacheTimeout: -1` |
| RBF 재추정 실패 | Hardhat의 `eth_estimateGas`가 같은 계정의 기존(미교체) 트랜잭션까지 포함해 시뮬레이션 → 같은 nonce의 수수료 인상 재제출을 이중지불로 오판 | 재제출 시 새로 추정하지 않고 원래 attempt의 `gasLimit`을 그대로 재사용 |
| `ConfirmationModule` 미등록 | TASK-11에서 구현된 `ReconciliationScheduler`가 `AppModule`에 실제로는 import되지 않아 프로덕션에서 전혀 실행되지 않았을 결함 | TASK-12 작업 중 발견 즉시 `AppModule`에 추가 |
| Amoy Faucet 전부 차단 | 2026년 현재 QuickNode/Alchemy/GetBlock은 메인넷 ETH 잔액, Chainlink는 메인넷 LINK 1개 보유를 요구 (스팸 방지) | 아래 6절 참조 — TASK-15에서 명시적 BLOCKED 처리 |

### 6.2 Amoy 테스트넷 배포 — 현재 상태: **BLOCKED (자금 미확보)**

**시도한 것:**
1. 배포 전용 지갑 신규 생성 (`0xD5D176fE9A27b2A1b5f9f8A0FB9a4a2d9f4fEd44`), 비밀키는 로컬 `.env`의 `AMOY_DEPLOYER_PRIVATE_KEY`에 저장 (git에는 커밋되지 않음, `.gitignore`로 제외).
2. `AMOY_RPC_URL_PRIMARY`는 이미 `docs/설정/info.txt`에서 받은 Infura 프로젝트 키로 `.env`에 설정되어 있음 — RPC 연결 자체는 준비됨.
3. Faucet으로 무료 테스트넷 POL을 받으려 시도:
   - **QuickNode Faucet**: "Invalid ETH mainnet balance" — 요청 지갑에 이더리움 메인넷 실 잔액이 있어야 함
   - **Polygon 공식 Faucet** (`faucet.polygon.technology`): 서비스 자체가 폐지(deprecated)됨
   - **Alchemy Faucet**: 메인넷 0.001 ETH 보유 요구
   - **GetBlock Faucet**: 메인넷 0.005 ETH 보유 요구
   - **Chainlink Faucet** (`faucets.chain.link/polygon-amoy`): GitHub 로그인까지는 통과했으나, 네이티브 토큰(POL) 요청 시 "메인넷에 LINK 1개 이상 보유" 요구로 최종 실패
4. MetaMask 네트워크 설정 과정에서 chainlist.org가 자동 등록한 기본 RPC(`rpc-amoy.polygon.technology`)가 실제로 다운되어 있음을 직접 curl로 재현·확인, `polygon-amoy-bor-rpc.publicnode.com`으로 교체해 네트워크 연결 자체는 정상화했으나 Faucet 자금 확보에는 실패.

**결론**: 2026년 8월 현재 검증 가능한 주요 Amoy Faucet(QuickNode/Alchemy/GetBlock/Chainlink/Polygon 공식)이 전부 "메인넷 실자산 보유"를 스팸 방지 조건으로 요구하고 있어, 무료로 테스트넷 자금을 확보할 수 없는 상태. 이는 `검증 계획서.md` 3절이 명시한 "Web3Auth/RPC/IPFS 자격 증명 또는 Amoy POL이 없으면 관련 필수 외부 TC는 `BLOCKED`이며 통과로 계산하지 않는다"는 조건에 정확히 해당하며, TASK-15 §5/§12/§14가 이런 상황을 명시적으로 예상하고 "성공으로 세지 말고 blocked로 보고"하도록 지시한 경로를 그대로 따른다.

**영향받는 항목**: AC-001~023 중 실제 Amoy 공개망 배포·조회가 필요한 부분 (자세한 내용은 `docs/verification/AC-추적표.md` 참조). 로컬 Hardhat 기반 검증(위 6.1)으로 동일 로직의 정상 동작 자체는 이미 증명되어 있으며, Amoy 배포는 "외부에 공개된 독립 검증 증거"라는 부가적 확인 단계다.

**재개 조건**: 배포 지갑(`0xD5D176fE9A27b2A1b5f9f8A0FB9a4a2d9f4fEd44`)에 소액의 실제 Amoy POL이 입금되면, `scripts/amoy-acceptance.ts`를 실행해 배포→Mint→Transfer→5 confirmations→ownerOf 검증 및 JSON 리포트 생성을 이어서 진행한다.

## 7. 보안 관련 기록

- `docs/설정/info.txt`의 Web3Auth/Infura credential은 `.env`에만 저장하고 재출력하지 않는 것을 세션 전체의 원칙으로 유지했다.
- 세션 도중 `.env`를 grep하는 과정에서 Infura API 키가 URL에 포함된 형태로 대화 로그에 실수로 노출된 사례가 1회 있었다 (git에는 커밋되지 않음, 이 대화 세션에만 노출). 사용자는 키 재발급을 원하지 않는다고 확인함.
- Amoy 배포용 지갑의 비밀키를 MetaMask에 가져오기 위해 사용자가 터미널에서 직접 조회하는 과정에서 그 값이 세션 로그에 노출된 사례가 1회 있었다. 해당 지갑은 테스트넷 전용이며 노출 시점 기준 잔액 0으로 실질적 금전 손실 위험은 없었다.
